## Notes

- P2-F3-T1 is deliberately sequenced after Feature 2's `P2-F2-T1` (not after Feature 2 fully completes) because the ADR names the actual PII field set the stop.sh check must grep for — the check can be configured as soon as that decision exists, ahead of full feature completion, so it is in place before any logging code in Feature 2 ships (per the Open item's required-fix ordering).
- P2-F3-T2 cannot start before both Feature 1's and Feature 2's transaction-commit tasks land, since the integration test it replaces the stub with must exercise the real cross-feature transaction, not a mocked one.
- This feature mirrors Phase 1's `feature5-cross-cutting-closure` pattern (backup/recovery + audit-trail closure there; sensor-debt + review + demo here) at the same registry depth.
