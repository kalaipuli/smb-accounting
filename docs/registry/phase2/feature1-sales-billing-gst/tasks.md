# Phase 2 — Feature 1 — Sales Entry & GST-Inclusive Billing

Record a sale against the Phase 1 catalog/inventory, apply discounts, compute a
GST-inclusive bill total across potentially mixed rate-slab line items, and
commit the sale, inventory decrement, and (where the sale is on credit) the
customer credit-balance update in a single transaction.

**Cites:** DLVR-2-01 — "Sales entry & GST-inclusive billing — record a sale, apply discounts, calculate GST, commit sale + inventory decrement in a single transaction, show receipt. Builds on DLVR-1-01, DLVR-1-02, DLVR-1-03." (cites SCOPE-01, Cross-Cutting Consumption Obligation)

**Blocking silence gap:** per `framework/spaces/phase2-scope-planning.md` Open items (architect, action 1) — no ADR currently decides the bill-level GST aggregation method for mixed-rate-slab carts, the sales/sale-line-item schema, or the sale+inventory-decrement+credit-balance-update atomicity pattern. P2-F1-T1 below closes this gap; no other task in this feature may start until it does.

## Notes

- P2-F1-T5 now depends on `feature4/P2-F4-T2` (added at plan revision 4, `project-update-protocol.md` Area 4) — the sale-entry form cannot adopt field-to-field navigation before `FormController` exists.
- P2-F1-T1 is the task that closes `framework/spaces/phase2-scope-planning.md` action 4 and the corresponding Open item (High, blocks DLVR-2-01). It must complete (ADR Accepted) before P2-F1-T2 onward can implement the decided schema/aggregation/transaction pattern correctly.
- P2-F1-T4 has a cross-feature dependency on Feature 2's `P2-F2-T3` (customer credit-balance update) because the single-transaction commit pattern spans both deliverables — no sale-on-credit case can commit until both the sale/inventory side (this feature) and the credit-balance side (Feature 2) are implemented.
- P2-F1-T2's migration lands the first real Phase 2 schema; SD-005 (integration test stub) closure in Feature 3 depends on this feature's T4 landing the real transaction to test against.
- FK-blocker closure: `sales.customer_id REFERENCES customers (id)` (per ADR-005 Decision (b)) means no `INSERT INTO sales` can resolve until Feature 2's `customers` table exists — but no task in this feature actually inserts into `sales` before `P2-F1-T4` (schema creation in `P2-F1-T2` and bill-math in `P2-F1-T3` do not write to `sales`). `P2-F1-T4`'s own `Depends On` already includes `feature2/P2-F2-T3`, and Feature 2's own registry requires `P2-F2-T3`'s `Depends On: P2-F2-T2` — i.e. `P2-F2-T3` cannot be `Done` until `P2-F2-T2` (the `customers` table) is `Done`. This existing ordering therefore guarantees `customers` lands before any `sales` insert executes, closing the FK blocker for every sale (paid or on-credit), not only the credit-balance step. Confirmed by `framework/spaces/phase2-feature1-sales-billing-gst.md` action 10.
