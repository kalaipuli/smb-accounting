## Findings

### [SEV-001] Unhandled `DiscountExceedsPriceError` crashes the catalog UI (Insecure Design / Availability) — RESOLVED

| Severity | Category | Location | CVE/Ref | Compliance |
|---|---|---|---|---|
| High (resolved) | Insecure Design (OWASP A04) / Improper Error Handling | `src/ui/catalog.py:180` (`_render_discounts`); `src/services/discounts.py:58-73` (`_validate_flat_value_against_price`) | N/A — internal design defect, not a published CVE | N/A |

**Description** — Original finding: `_render_discounts` called `apply_discount` with no exception handling, and `_validate_discount` performed no write-time check of a flat discount's value against the product's current price.

**Root Cause** — Same as original review; see 2026-08-01 disposition (superseded content preserved in this space's Reference notes).

**Impact** — Same as original review.

**Verification of fix (2026-08-02)** — Independently re-read the current committed code, not the architect's or backend-developer's summary:
- `src/ui/catalog.py:179-189` — `_render_discounts` now wraps `apply_discount(product.price, discount)` in a per-row `try/except DiscountExceedsPriceError`, rendering `"(no longer valid at current price)"` and `continue`-ing to the next row instead of propagating. Confirmed by direct read.
- `src/services/discounts.py:58-73` — new `_validate_flat_value_against_price` helper queries the product's current price via direct SQL (`SELECT price FROM products WHERE id = ?`) and raises `DiscountValidationError` if a flat discount's value exceeds it; called from both `create_discount` (line 87) and `update_discount` (line 122), i.e. at write time, before either INSERT/UPDATE executes. Confirmed by direct read.
- Test coverage confirmed by direct read of `tests/unit/services/test_discounts.py` (`test_create_discount_when_flat_value_exceeds_price_raises_validation_error`, `test_update_discount_when_flat_value_exceeds_price_raises_validation_error`) and `tests/unit/ui/test_catalog.py` (`test_render_discounts_when_flat_discount_exceeds_current_price_shows_degraded_state_and_does_not_raise`, `test_render_discounts_when_discount_within_price_shows_discounted_value`).
- `poetry run pytest tests/unit/ -q --tb=short` → `96 passed` (this turn). `poetry run mypy src/services/discounts.py src/ui/catalog.py --strict` → `Success: no issues found in 2 source files` (this turn).

Both the write-time gap (flat discount created larger than price) and the read-time gap (price lowered after discount creation) are now covered — the defense-in-depth fix specified in the original Proposed Fix was implemented in full, not partially. **Status: Resolved.**

### [SEV-002] Dependency version ranges are not exact-pinned in `pyproject.toml` — RESOLVED

| Severity | Category | Location | CVE/Ref | Compliance |
|---|---|---|---|---|
| Medium (resolved) | Vulnerable/Outdated Components (supply chain) | `pyproject.toml:9-17` | N/A — governance gap, not a specific CVE | N/A |

**Description** — Original finding: all four dev dependencies used caret ranges instead of exact pins.

**Verification of fix (2026-08-02)** — `pyproject.toml` read directly this turn: `pytest = "9.1.1"`, `ruff = "0.16.1"`, `mypy = "2.3.0"`, `vulture = "2.16"`, `pytest-cov = "7.1.0"` — all five dev-group entries are exact-pinned (no `^`/`~` prefix), matching the `poetry.lock`-resolved versions exactly. `python = "^3.12"` in `[tool.poetry.dependencies]` remains a caret range by design — this is the Python interpreter constraint, not a package pin, and is outside the scope of the exact-pin rule (`python.md` § Dependency Management targets package dependencies, not the interpreter version selector). **Status: Resolved.**
