## Migration Review

**Zero-downtime ruling:** Not required for this migration. All three tables (`products`, `discounts`, `inventory_stock`) are newly created in `0001_up.sql` — this is the project's first migration against an empty SQLite file, so there is no live table with production traffic to protect. The expand/contract pattern in `framework/guidelines/database-migrations.md` applies to changes on tables carrying existing data (column drop, rename, type change). No such change is present here. This ruling only covers migration `0001` — any future migration that drops, renames, or narrows a column on `products`, `discounts`, or `inventory_stock` once rows exist will require expand/contract and a separate DBA review.

**Rollback:** `0001_down.sql` exists and drops all three tables in reverse foreign-key dependency order (`inventory_stock`, `discounts`, `products` — both `inventory_stock.product_id` and `discounts.product_id` reference `products.id`). Confirmed correct: dropping `products` first would fail to satisfy the FK dependency ordering requirement if enforcement were active at DDL execution time. No Critical finding — `database-migrations.md` Core Rule 2 (every migration has a corresponding rollback script) is satisfied.

**Idempotency:** `0001_up.sql` uses `CREATE TABLE IF NOT EXISTS` for all three tables; `0001_down.sql` uses `DROP TABLE IF EXISTS` for all three tables. Both directions are safe to re-run if interrupted mid-execution — satisfies `database-migrations.md` Core Rule and this persona's idempotency check.

**Time window:** Both migration files execute DDL only against an empty database (no data volume). No time-window concern.

**Schema/migration consistency:** `src/db/schema.py` `SCHEMA_STATEMENTS` and `0001_up.sql` DDL are identical for all three tables (column names, types, constraints, defaults) — confirmed by direct comparison. No drift between the two authoritative definitions.

### [DB-001] discounts.product_id has no supporting index — informational, not a defect

| Severity | File | Rule |
|---|---|---|
| Low | src/db/schema.py, src/db/migrations/0001_up.sql | database-migrations.md § Index Strategy |

**Issue:** `discounts.product_id` is a foreign key to `products.id` but has no index (SQLite does not auto-index FK columns the way it auto-indexes `PRIMARY KEY` columns). Once Feature 3 (Catalog & Pricing) implements a "list discount rules for product X" query, that query will do a full table scan of `discounts` until an index is added.

**Fix:** No fix required in this migration. No application query against `discounts` exists yet (schema-only migration), so citing a query pattern now would be speculative — `database-migrations.md` explicitly prohibits adding indexes without a cited query pattern ("MUST NOT add indexes on every column 'just in case' — add based on measured query patterns"). Recorded here as a forward-looking note: when Feature 3 introduces the product→discounts lookup, a follow-up migration should add `CREATE INDEX idx_discounts_product_id ON discounts (product_id)`, citing that query pattern explicitly, and route through this Migration Review Gate before merge. `product_id` cardinality will scale with the product catalog (expected to be well above the 10-distinct-value floor for a kirana shop catalog), so it is a legitimate index candidate once the query exists — not a low-cardinality anti-pattern.

## Index Strategy Review

No indexes are added by this migration beyond the implicit ones SQLite creates for declared `PRIMARY KEY` columns (`products.id`, `inventory_stock.product_id`). Both are justified: `products.id` is the primary lookup key for every downstream join (discounts, inventory, and future sales lines); `inventory_stock.product_id` as primary key is correct for a one-row-per-product current-state table (per ARCH-D04 — "current state only; history via transaction log") and simultaneously serves as the FK-supporting index for that table, so no separate index is needed there. See [DB-001] above for the one identified future index need (`discounts.product_id`) — not added now because no query pattern exists yet to justify it.

No duplicate indexes present (only two implicit primary-key indexes exist across the three tables, on distinct columns).

No boolean or low-cardinality column indexes present — none of the three tables declare a boolean column at all.

## discounts table column design — explicit confirmation

`discounts(product_id, discount_type, value)` as authored in action 1 is **confirmed** as an adequate MVP design:

- `product_id INTEGER NOT NULL REFERENCES products (id)` — correctly scopes every discount rule to a single product, matching DLVR-1-02 ("discount rules") and the absence of any store-wide-discount requirement in `project-plan.md` / `architecture.md`.
- `discount_type TEXT NOT NULL CHECK (discount_type IN ('percentage', 'flat'))` — a bounded enum via `CHECK`, not a magic string; avoids the low-cardinality index anti-pattern by not being indexed (2 distinct values would fail the < 10 distinct value threshold if indexed — correctly left unindexed).
- `value NUMERIC NOT NULL CHECK (value >= 0)` — non-negative constraint enforced at the DB layer, correct defensive design for a monetary/percentage field with no signed-value use case named anywhere in scope.

**Gap noted, not blocking:** no validity window (`start_date`/`end_date`) or `is_active` flag. No source (`project-plan.md`, `architecture.md`, `project-context.md`) specifies time-boxed or togglable discount rules for MVP scope — adding either column now would be an unrequested/unspecified addition, not a correction of a defect. If a future task requires deactivating or time-limiting a discount rule without deleting history, that is new scope requiring its own ADR/task, not a retroactive change to this migration (`database-migrations.md` Core Rule 3 — MUST NOT modify a released migration).
