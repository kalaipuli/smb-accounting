# Security Review Report

**Date:** 2026-08-10
**Scope:** Phase 3 Feature 1 (Product Cost Capture & COGS Snapshot) + Feature 2 (P&L Reporting), bundled Tier 2 review, per user decision 2026-08-10 recorded in Feature 1's `tasks.md` DoD Gate note
**Reviewer:** Security Reviewer Agent
**Overall Risk:** Low
**Verdict:** APPROVED

## Executive Summary

This is the bundled Tier 2 security review for Phase 3 Feature 1 (cost column + per-line COGS snapshot) and Feature 2 (P&L aggregation service + three-page reporting UI), covering `docs/adr/ADR-008` and `docs/adr/ADR-009`. Scope: the new `products.cost` / `sale_line_items.unit_cost` columns, the `PLReport` aggregation service, the three reporting UI pages, and the main-menu wiring that exposes them.

Cost-data classification was independently confirmed: `products.cost` and `sale_line_items.unit_cost` are **Internal**, non-PII data under the existing `ARCH-D03` (product pricing catalog) and `ARCH-D02` (sales/transaction records) classification rows — no new `ARCH-D` row was required, matching ADR-009's own Compliance Posture statement, verified against `framework/project/architecture.md` directly rather than trusting the ADR's assertion alone.

The `unit_cost` non-render prohibition on the customer-facing bill/receipt (ADR-009 Decision (b) interface-contract row) was independently re-verified two ways: (1) a fresh `grep` for the literal string `unit_cost` in `src/ui/sales.py` and `src/ui/customers.py` returns no match; (2) the governing regression test (`tests/unit/ui/test_sales.py`, P3-F1-T6) was opened and read directly — both `test_render_receipt_when_line_items_have_known_unit_cost_does_not_render_it` and `test_render_history_detail_when_line_items_have_known_unit_cost_does_not_render_it` construct a sale with a non-NULL `unit_cost`, render it, and assert `"unit_cost" not in rendered_text.lower()` — a genuine negative assertion, not merely "renders without raising". The reporting UI (`src/ui/reports.py`) never references `unit_cost` at all; only the aggregated `cogs`/`net` figures reach any screen.

A live dependency CVE audit was run (`pip-audit`, not inferred from memory) against the resolved environment. No CVE was found in any of this project's declared dependencies (`pytest 9.1.1`, `ruff 0.16.1`, `mypy 2.3.0`, `vulture 2.16`, `pytest-cov 7.1.0` — all exact-pinned in `pyproject.toml`/`poetry.lock`, unchanged since the 2026-08-01 review). The audit flagged 4 known advisories against `pip 26.0.1` itself — the ambient package-installer binary in the local virtualenv, not a project-declared dependency in `pyproject.toml`. This is recorded as a single Low/Informational finding below (dev-tooling hygiene), not a Critical/High blocker, and does not affect the shipped application (this is an offline single-user CLI tool with zero runtime third-party dependencies — `pyproject.toml [tool.poetry.dependencies]` contains only `python`).

No injection risk was found in the new aggregation queries — every `sqlite3` call in `src/services/reporting.py` is fully parameterized (`?` placeholders, tuple bindings); f-strings are used only for exception messages and display labels, never to build SQL text. No secrets, credentials, or `.env` files are introduced by this feature (this stack has no external credentials — `SMB_REPORTING_TZ_OFFSET_MINUTES` is a local numeric offset, not a secret). No new logging call was introduced in `src/services/reporting.py` or `src/ui/reports.py` — cost figures are never logged, consistent with ADR-009's explicit "no service module in this codebase logs today, and none should begin logging cost" statement, independently confirmed by `grep`.

**0 Critical, 0 High, 0 Medium findings open.** 1 Low/Informational finding (dev-environment `pip` advisories, not a project dependency) — does not block Tier 2 sign-off.

## Findings

### [SEV-001] `pip` (ambient venv installer, not a declared project dependency) carries 4 open advisories

| Severity | Category | Location | CVE/Ref | Compliance |
|---|---|---|---|---|
| Low / Informational | Vulnerable/Outdated Components (supply chain, dev tooling) | Local `.venv` package installer (`pip 26.0.1`) — not referenced anywhere in `pyproject.toml` or `poetry.lock` | PYSEC-2026-196 (alias CVE-2026-8643, GHSA-wf93-45jw-7689, CVSS 5.5 Medium); PYSEC-2026-2875; PYSEC-2026-2876 | N/A — dev-environment hygiene, no regulatory framework applies to this offline single-user tool |

**Description** — `pip-audit` (installed and run live this turn against the project's `.venv`) reports the venv's bundled `pip` binary, version `26.0.1`, as carrying 4 known advisories, the most notable being `PYSEC-2026-196`/`CVE-2026-8643`: pip historically treated `console_scripts`/`gui_scripts` entry-point names as filesystem paths without sanitizing the resolved absolute path, allowing an entry point to be installed outside the intended installation directory. Fixed in `pip 26.1.2`.

**Root Cause** — `pip` is not a project-declared dependency (it is not listed in `pyproject.toml`); it is the ambient installer that ships with the Python interpreter/virtualenv used for local development and CI. Its version drifts with the base Python/virtualenv toolchain, independent of this feature's `poetry.lock`.

**Impact** — Exploitation requires an attacker-controlled package (with a malicious `console_scripts`/`gui_scripts` entry) being installed via this `pip` at package-install time; it is a supply-chain/installation-time risk to the development and CI environment, not to the running application (this project has zero runtime third-party dependencies, and the shipped artifact does not invoke `pip` at runtime). No exploitation path exists via any code this review's scope touches (`src/services/reporting.py`, `src/ui/reports.py`, or any Phase 3 module).

**Proposed Fix** — Upgrade the local/CI virtualenv's `pip` to `≥ 26.1.2` (`pip install --upgrade pip` as part of environment setup, or pin the CI base image's pip version). This is an environment/CI configuration change, not an application code change — no action in this space owns `pyproject.toml`'s Python interpreter/toolchain provisioning, so this is recorded as a tracked open item rather than a blocking Tier 2 condition, per the Low severity rating (defence-in-depth gap on dev tooling, not exploitable through this feature's shipped code).

## Compliance Notes

- **Data classification** — `products.cost` (Internal, `ARCH-D03` — "Product pricing catalog — Internal") and `sale_line_items.unit_cost` (Internal, `ARCH-D02` — "Sales/transaction records — Internal — Indefinite"), both re-confirmed directly against `framework/project/architecture.md` this turn — neither column is PII, so no new `ARCH-D` row is required; this matches ADR-009's own Compliance Posture statement, independently verified rather than trusted. `PLReport`'s eleven fields (`period_label`, `period_start_utc`, `period_end_utc`, `revenue`, `discounts`, `cogs`, `net`, `credit_sales`, `line_count`, `lines_missing_cost`, `cost_complete`) carry no PII and no per-line/per-customer identifiers — confirmed by direct read of `src/services/reporting.py`'s `PLReport` dataclass; the aggregation queries in `_aggregate` join `sale_line_items`/`sales` only and never touch `customers`.
- **`unit_cost` non-render interface contract (ADR-009 Decision (b))** — independently re-verified this turn (not a re-statement of architect's or tester's prior finding): `grep -n "unit_cost" src/ui/sales.py src/ui/customers.py` → no match; `tests/unit/ui/test_sales.py` read directly — both P3-F1-T6 regression tests assert the negative condition (`"unit_cost" not in rendered_text.lower()`) against a sale line with a known, non-NULL `unit_cost`, not merely that rendering does not raise.
- **Least privilege / tenant isolation** — N/A, single-shop single-user local file (`ARCH-P01`), unchanged from prior reviews.
- **Audit trail** — `products.updated_at` records that a cost edit occurred but not the prior value; ADR-009 Consequences accepts this explicitly because the per-line `unit_cost` snapshot preserves the only prior value reporting depends on. No new audit-trail gap introduced by this feature beyond the one ADR-009 already discloses and accepts. `SD-002` (pre-existing open audit-trail item from the 2026-08-01 review) is unrelated to this feature's scope and is not re-opened or re-scoped here.
- **Secrets & configuration** — no secret or credential is introduced. `SMB_REPORTING_TZ_OFFSET_MINUTES` is a local numeric offset (not a secret), read via `os.environ.get` in `src/config.py::get_reporting_tz()`, mirroring the existing non-secret `SMB_DB_PATH` pattern — no `.env` file, no hardcoded credential, confirmed by direct read.
- **Logging** — `grep -rn "cost\|unit_cost" src/services/reporting.py src/ui/reports.py` shows no logging call referencing either field; no log statement of any kind exists in either new module (this offline tool has no `structlog` requirement per `project-context.md` §2, and neither module calls stdlib `logging` either).
- **Injection (OWASP A03)** — every SQL statement in `src/services/reporting.py::_aggregate` uses `?` parameter placeholders with tuple bindings (`(start_utc, end_utc)`); no f-string or `.format()` call builds SQL text anywhere in the module — confirmed by direct grep and read.
